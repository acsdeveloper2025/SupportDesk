# ADR-0010: Workflow definition MVP (E11-I01)

Status: Accepted

## Context

Workflow automation is described in [../09-ticket-lifecycle.md](../09-ticket-lifecycle.md) and [../workflow-matrix.md](../workflow-matrix.md). E11-I01 must let Tenant Admins define safe automation rules without shipping the execution engine. Open questions around deep validation and runtime dispatch are split across E11-I02 and E11-I03.

## Decision

Adopt the following MVP semantics for E11-I01:

1. **JSON-on-version storage:** Triggers, conditions, and actions are stored as JSON columns on immutable `workflow_versions` rows. The container `workflows` row holds tenant-scoped metadata (key, name, priority, enabled/pause state).
2. **Full catalog declared:** Trigger types, condition fields/operators, and action types are enumerated in domain code (`WorkflowDefinition`). Unknown values fail structural validation at create/draft update.
3. **Draft / published / retired:** Mutable drafts and immutable published versions follow ADR-005 (version published configuration). Publishing retires the prior published version; draft edits never mutate published rows.
4. **Pause vs retire:** Pause toggles `enabled` on the workflow container without retiring published versions. Soft delete sets `deleted_at` and hides from ordinary reads while preserving audit and version history.
5. **AND conditions:** All conditions on a version are ANDed. Condition grouping and NOT semantics are deferred to E11-I02.
6. **No execution:** No event subscription, matching, action dispatch, `workflow_executions`, or `workflow_action_attempts` writes in this slice.
7. **Structural validation only:** Validate catalog membership, ordinals, required action params, and positive integer priority. Reference checks (assignee/group existence), cycle detection, and ticket transition legality at publish are deferred to E11-I02.
8. **Priority uniqueness:** Application-enforced among non-deleted workflows per tenant. No database unique constraint on priority alone (soft delete must allow priority reuse).

## Alternatives considered

- Single JSON blob on `workflows` without versions: contradicts ADR-005 and breaks publish immutability.
- DB unique on priority: blocks priority reuse after soft delete without a contraction migration.
- Ship execution in E11-I01: expands blast radius before validation and RBAC surfaces are proven.
- Arbitrary script actions: rejected for security; bounded action catalog only.

## Consequences

- APIs under `/api/v1/workflows` are definition-only; execution endpoints remain unimplemented until E11-I03.
- Audit events: `workflow.created`, `workflow.draft_updated`, `workflow.published`, `workflow.paused`, `workflow.resumed`, `workflow.deleted`.
- Permissions: `workflow.read`, `workflow.create`, `workflow.update`, `workflow.publish`, `workflow.pause` per [../permissions-matrix.md](../permissions-matrix.md).
- E11-I02 must extend publish validation without breaking published immutability.
- E11-I03 must read published versions in priority order and honor pause/soft-delete flags.
