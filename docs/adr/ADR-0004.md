# ADR-0004: Authentication milestone RBAC foundation

Status: Accepted for M2 implementation

## Context

The final planning prompt for M2 narrows the database scope to authentication and identity foundation tables: Tenants, Users, Roles, Permissions, UserRoles, RolePermissions, Sessions, RefreshTokens, and authentication Audit Logs. Earlier architecture documents also describe richer future tenant membership, group membership, organization, and operator-elevation structures.

The milestone must provide tenant-aware authentication and permission checks without implementing Organizations, Tickets, Workflows, SLA, Notifications, Reports, Search, or Dashboard features.

## Decision

For M2, implement direct tenant-scoped `user_roles` assignments as the RBAC foundation. A `user_roles` row links a User, Tenant, and Role and can be revoked independently. Role grants are evaluated through `role_permissions`.

Tenant membership for authentication is represented by active tenant-scoped role assignment during M2. Richer membership tables, organization/group assignment, and delegated administration remain reserved for later milestones when those domains are implemented.

Database constraints must keep role assignments tenant-consistent. `user_roles` and `role_permissions` reference `roles` through composite `(role_id, tenant_id)` constraints so a role from one tenant cannot be attached to another tenant's assignment or grant.

## Alternatives considered

- Implement `tenant_memberships` and `membership_roles` immediately: closer to the broader ERD, but expands this milestone beyond the prompt and introduces group/organization administration decisions before their issues start.
- Use direct `user_roles` for M2: smaller Auth/Identity scope and enough for tenant-aware auth and RBAC foundation, with a documented migration path to richer memberships.

## Consequences

- Authentication and RBAC checks must always include `tenant_id`.
- Sessions and refresh tokens are tenant-scoped in M2; authentication cannot create cross-tenant or tenantless user sessions.
- Users without an active tenant-scoped role assignment are not considered active tenant participants in M2.
- Future membership work must either migrate from `user_roles` into `tenant_memberships`/`membership_roles` or preserve `user_roles` as a compatibility projection.
- No business permission behavior is introduced by this decision.
