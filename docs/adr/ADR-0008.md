# ADR-0008: Reject group assignment until Organizations/Groups exist

Status: Accepted for Ticket Module v1

## Context

The Ticket schema includes `assigned_group_id` for future group queues, but Organizations (M3) and groups tables are not implemented. Accepting arbitrary UUIDs would store unverifiable references and break tenant integrity expectations.

## Decision

Until a Groups (or equivalent) aggregate ships with tenant-scoped FK validation:

1. Ticket **assign** APIs reject any non-null `assignedGroupId` with HTTP `400` and a stable validation message.
2. Column `assigned_group_id` remains nullable for forward-compatible schema.
3. Unassign continues to clear both assignee and group fields.

User assignment (`assigneeUserId`) remains supported with ACTIVE tenant membership checks.

## Alternatives considered

- Allow opaque group UUIDs: simple, but creates orphan references.
- Implement Organizations/Groups now: out of scope for hardening (new product surface).

## Consequences

- Clients must assign users only in v1.
- Docs and OpenAPI describe the rejection.
- When Groups ship, remove the rejection and add FK + membership validation in the same PR.
