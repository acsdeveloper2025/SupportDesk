# ADR-0001: Multi-tenancy approach

Status: Accepted assumption pending OQ-02 validation

## Context

SupportDesk is a commercial multi-tenant Ticketing SaaS. [06-tenant-isolation.md](../06-tenant-isolation.md) requires every customer-owned record and execution path to carry immutable Tenant context. Data residency, dedicated-region needs, and tenant mobility remain open in [../decision-log.md](../decision-log.md) OQ-02.

## Decision

Begin with shared application infrastructure and shared logical data stores using strict row-level tenant ownership, tenant-scoped object storage keys, tenant-aware caches/search indexes, and source-of-truth authorization rechecks.

Tenant context is resolved from authenticated membership and trusted routing. It is propagated through API, service, data-access, queue, outbox, file, search, reporting, telemetry, backup, restore, and operator tooling boundaries.

Dedicated database, schema, storage, or region placement is reserved as a future isolation tier for contractual, regulatory, scale, or enterprise-plan requirements.

## Alternatives considered

- Dedicated database per tenant: stronger blast-radius reduction but high operational overhead before residency/scale requirements are known.
- Dedicated schema per tenant: simpler logical separation but complicates migrations and cross-tenant fleet operations.
- Shared row-level isolation: fastest path with strong controls if rigorously tested; accepted for initial design.

## Consequences

- All tenant-owned tables need immutable `tenant_id` and tenant-aware constraints.
- Tenant-isolation negative tests are release gates.
- Caches, queues, search, exports, backups, and telemetry must include tenant separation controls.
- Future dedicated isolation tiers require migration, routing, backup, and restore design.
