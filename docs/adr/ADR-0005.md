# ADR-0005: Browser authentication transport

Status: Accepted for M2 implementation

## Context

M2 authentication issues created tenant-scoped sessions, signed JWT access tokens, refresh-token rotation, and authentication audit logging. Some active-session endpoints still accept `x-session-id` as a temporary development transport, and login/refresh responses currently expose token material in JSON for API verification.

The web application now needs login, password recovery, email verification, and profile screens. Those screens must not store refresh tokens, session identifiers, or long-lived credentials in browser-readable storage. [../07-security-compliance.md](../07-security-compliance.md) also requires CSRF protection where cookie-authenticated.

## Decision

Use a same-origin Next.js Backend-for-Frontend (BFF) for browser authentication.

The browser authenticates with the Next.js web app origin. The BFF exchanges credentials and refresh tokens with the NestJS API server-side, stores browser session material only in `HttpOnly`, `Secure`, `SameSite=Lax` cookies, and forwards authenticated API calls from server-side route handlers. Refresh tokens must never be readable by browser JavaScript or persisted in `localStorage` or `sessionStorage`.

The BFF owns browser CSRF protection. Every cookie-authenticated state-changing request must include a CSRF token/header pair validated by the BFF before proxying to the API. CSRF tokens are not authentication credentials and may be exposed to browser JavaScript only for header submission.

API-to-API and non-browser clients continue to use documented bearer-token flows. The development-only `x-session-id` transport must be retired from protected browser flows as the access-token guard and current-identity API are implemented.

Cookie policy:

- Production cookies use `HttpOnly`, `Secure`, `SameSite=Lax`, scoped paths, and explicit expiry.
- Local development may omit `Secure` only when running on `http://localhost`.
- Refresh/session cookies are rotated or cleared on login, refresh, logout, password change, reset completion, and token-family replay.
- Browser mutations use CSRF validation before any credentialed API call.

## Alternatives considered

- Direct browser-to-API bearer tokens: simpler API surface, but forces access-token storage decisions into client JavaScript and makes refresh-token protection harder to review.
- Direct browser-to-API cookies: viable, but CORS, CSRF, and subdomain policy become more complex before the product needs cross-origin deployment.
- Same-origin Next.js BFF: keeps browser credentials behind `HttpOnly` cookies, centralizes CSRF handling, and gives frontend screens a stable same-origin API.

## Consequences

- Frontend auth pages must call same-origin BFF routes, not persist API tokens directly.
- Protected API controllers need a reusable access-token guard and current identity context so the BFF can proxy requests safely.
- Swagger must describe both bearer-token API clients and browser BFF behavior.
- CSRF tests are required for cookie-authenticated browser mutations.
- Local development documentation must explain cookie behavior across web and API ports.
- Future Ticket APIs can rely on the same authenticated request context for tenant isolation and RBAC checks.
