# ADR-0012: Workflow runtime with shared transactional outbox

Status: Accepted for E11-I03 implementation planning

## Context

Decision-log [ADR-004](../decision-log.md) requires atomic domain + audit + outbox commits and at-least-once async processing. [ADR-0007](ADR-0007.md) deferred outbox implementation until automation consumers existed. E11-I01/I02 deliver workflow definition and validation without execution. E11-I03 must run deterministic automation from domain events without coupling API latency to workflow work, while preventing infinite automation loops and duplicate effects under replay.

## Decision

1. **Implement the transactional outbox as part of E11-I03** (same milestone as the workflow runtime), lifting the ADR-0007 deferral. Decision-log ADR-004 remains the binding target.
2. **Use one shared `outbox_events` table** and a single claim/dispatch worker with typed handlers. Workflow evaluation is the primary consumer in this milestone.
3. **Keep the request path fully async:** mutations commit domain state, audit evidence, and outbox intent only; workers perform matching and actions.
4. **Execute one DB transaction per workflow action**, resuming from `workflow_action_attempts` after retries. Workflows for one event run sequentially by priority; actions run sequentially by ordinal.
5. **Bound recursion with `automationDepth`** on outbox events (platform hard max 3; tenants may only lower). Depth-capped events skip further workflow evaluation but do not roll back the producing domain write.
6. **Retry transient failures with bounded backoff**, then dead-letter; emit `workflow.execution_failed` audit and ops notification intents. Optionally auto-pause a workflow after a dead-letter threshold in a time window.
7. **Guarantee exactly-once effects** via dedupe keys on outbox publish, `workflow_executions`, `workflow_action_attempts`, domain action idempotency keys, and `notification_intents` — not exactly-once delivery.
8. **Implement minimal notification intents** for `create_notification` (deduped, no provider delivery). Call the existing SLA module in-process for `sla_start` / `sla_stop`.

Detailed contracts live in [../superpowers/specs/2026-08-01-workflow-runtime-design.md](../superpowers/specs/2026-08-01-workflow-runtime-design.md).

## Alternatives considered

- **Separate outbox milestone before E11-I03:** cleaner ownership, slower path to a working runtime; rejected in favor of one milestone with a written design.
- **Inline/sync workflow execution on the API path:** better “already applied” UX; rejected because it couples latency and failure domains to automation.
- **Dual queue (domain outbox → workflow_jobs):** isolates backlogs; rejected as duplicate claim/retry machinery for this stage.
- **Per-module outbox tables:** stronger isolation; rejected as fighting ADR-004’s single outbox model in the modular monolith.
- **Suppress all automation-originated re-evaluation:** stronger loop break; rejected because legitimate follow-on rules would be missed — depth budget preferred.
- **Defer `create_notification` until full E08:** keeps E11-I03 smaller; rejected to keep the published catalog honest with real intent writes.

## Consequences

- Ticket/comment/SLA warning-breach writers must append outbox rows in the same transaction before E11-I03 is considered done.
- A background claimer becomes a required runtime process (lease, backoff, dead-letter, metrics on backlog age/depth).
- Workflow actions must be idempotent and go through domain services with tenant context and an automation actor.
- Provider notification delivery, webhooks, schedules, and custom scripts remain out of scope.
- ADR-0007’s “do not implement outbox yet” deferral is superseded for implementation timing; its requirement that automation depend on outbox remains satisfied by this ADR.
- Admin outbox inspect/replay APIs become necessary operational controls.
- Tests must cover atomic append, replay safety, depth cap, tenant isolation, and dead-letter/auto-pause behavior.

## Security and tenant impact

- Every outbox, execution, attempt, and intent row is tenant-scoped; claim batches must not cross tenants inside one processing unit of work.
- Fail closed if tenant context is missing on worker paths.
- Error messages and timeline summaries must not leak cross-tenant existence or secrets.
- Automation must not bypass transition legality or tenant isolation checks.

## Operational impact

- New worker process/pool; dashboards for outbox backlog depth, oldest pending age, dead-letter count, and workflow failure rate.
- Runbooks for replay, lease stuck claims, and auto-paused workflows.
- Retention for append-only execution history follows later retention policy work.
