# Table catalogue

This catalogue defines intended tables and invariants. It is not SQL. Naming follows [NAMING-CONVENTIONS.md](NAMING-CONVENTIONS.md); indexing follows [INDEXING.md](INDEXING.md).

## Identity and tenant administration

| Table              | Purpose                                                                                               | Primary key | Tenant key           | Key constraints                                                                         |
| ------------------ | ----------------------------------------------------------------------------------------------------- | ----------- | -------------------- | --------------------------------------------------------------------------------------- |
| `tenants`          | Customer isolation boundary and lifecycle root.                                                       | `id`        | none                 | Unique `slug`; unique `public_id`; lifecycle state required.                            |
| `tenant_settings`  | Versioned tenant configuration such as branding, locale, security, quotas, and support access policy. | `id`        | `tenant_id`          | Unique `(tenant_id, namespace, version)`.                                               |
| `tenant_domains`   | Verified domains for tenant routing, email, and identity discovery.                                   | `id`        | `tenant_id`          | Unique domain globally; verification state required.                                    |
| `users`            | Global human identity.                                                                                | `id`        | none                 | Unique `email_normalized`; state, verification, lockout, and password fields.           |
| `user_profiles`    | User display profile and locale/time-zone attributes.                                                 | `id`        | through `user_id`    | Unique `user_id`.                                                                       |
| `user_preferences` | User identity-scope preferences.                                                                      | `id`        | through `user_id`    | Unique `user_id`.                                                                       |
| `sessions`         | Tenant-scoped user session/device state and revocation.                                               | `id`        | `tenant_id`          | Expiry, revocation, remember-me, and device metadata required.                          |
| `refresh_tokens`   | Tenant-scoped refresh token families and rotation/reuse evidence.                                     | `id`        | `tenant_id`          | Unique `token_hash`; family, state, revocation, and expiry required.                    |
| `auth_tokens`      | Tenant-scoped one-time tokens for email verification and password recovery.                           | `id`        | `tenant_id`          | Unique `token_hash`; purpose, state, expiry, and one-time use required.                 |
| `roles`            | Tenant-scoped role definitions.                                                                       | `id`        | `tenant_id`          | Unique `(tenant_id, key)` and `(tenant_id, name)`; system roles protected.              |
| `permissions`      | Stable global permission catalogue.                                                                   | `id`        | none                 | Unique `key`; never reused with changed meaning.                                        |
| `user_roles`       | M2 tenant-scoped user-to-role assignment; see [ADR-0004](../adr/ADR-0004.md).                         | `id`        | `tenant_id`          | Unique `(tenant_id, user_id, role_id)`; composite role/tenant FK required.              |
| `role_permissions` | Role-to-permission grants with scope.                                                                 | `id`        | `tenant_id`          | Unique `(tenant_id, role_id, permission_id, scope)`; composite role/tenant FK required. |
| `audit_events`     | Immutable authentication/security evidence for M2.                                                    | `id`        | optional `tenant_id` | Actor, action, outcome, correlation, and timestamps recorded.                           |

## Ticketing

### As-built (Ticket Module v1)

| Table      | Purpose                         | Primary key | Tenant key  | Key constraints                                                                                                                               |
| ---------- | ------------------------------- | ----------- | ----------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `tickets`  | Canonical support aggregate.    | `id`        | `tenant_id` | Unique `(tenant_id, public_ref)`; requester FK; optional assignee FK; soft delete; version. Indexes: status, assignee, requester, deleted_at. |
| `comments` | Public/internal ticket messages | `id`        | `tenant_id` | Ticket FK; author FK; soft delete; timeline index `(tenant_id, ticket_id, created_at)`; deleted_at index.                                     |

`assigned_group_id` exists on `tickets` for forward compatibility but is rejected by APIs until Groups ship ([ADR-0008](../adr/ADR-0008.md)).

## Soft delete and retention

Soft deletion is a lifecycle state, not an authorization bypass. Soft-deleted records remain tenant-scoped, hidden from ordinary reads, visible through authorized audit/recovery flows, and excluded from active uniqueness only when policy explicitly permits key reuse. Legal hold overrides deletion. Retention jobs must record audit events and preserve referential integrity.
